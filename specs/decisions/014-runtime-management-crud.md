# ADR-014: Runtime management CRUD — the management boundary becomes mutation-capable

## Status

Accepted

## Context

The management boundary is observation-only: [gateway-management.md](../contracts/gateway-management.md) sanctions exactly three mutations (the two auth actions on the session store and the discovery facility's retain-last-good metadata-store swap), its reads are in-memory except for the operator-triggered live upstream listing ([ADR-011](./011-management-live-model-listing.md)), and its Data Flow states there are "no file reads at request time" — the gateway keeps no state beyond the config file, and the config file changes only by a hand edit plus a full process restart. Runtime CRUD over the gateway's own configuration (upstreams, clients, model aliases) closes that gap, and the boundary's own checklist demands this document first: the Breaking Change Checklist item 3 says any further mutating endpoint on `/api/*` "requires a new ADR and the contract-plus-security-model updates before implementation". This is that ADR; the contract and [security-model.md](../architecture/security-model.md) updates land in the same change as the endpoints.

The decision revokes the read-only posture in exactly the direction item 3 provides for: the "frozen at startup" character of the facts the reads report ([ADR-011](./011-management-live-model-listing.md)) becomes a property of the moment between mutations, and the boundary's request-time upstream contacts grow from the operator-triggered listing to the enumerated live facilities the contract names. The ADR bar is met on both clauses: the decision is cross-cutting (HTTP → config → upstreams → gateway core → both HTTP surfaces) and contradicts documented invariants, so it is an ADR plus contract and security-model updates, never a quiet edit.

## Decision

- **D1 — Mutations write back to config.json; the config stays the single source of truth.** Every mutating endpoint serializes the post-change configuration, runs it through the startup validator (`src/config/schema.ts` — strict keys, every problem collected), writes it to a sibling temp file, and moves it onto `config.json` with an atomic rename. The in-memory mutation (D2) applies only after the write succeeded: a validation problem or a failed write leaves both disk and memory untouched, so the file on disk and the state in memory never diverge — the config file remains the one authority a restart reconstructs everything from. The gateway gains exactly one runtime file write (this one) and nothing else.
- **D2 — Hot apply without a restart.** After a successful write the process rebuilds the assembled graph in place — the upstream registry, the routing table ([ADR-009](./009-alias-table-routing.md)), the client-key digests inside the LLM gate, and the metadata-store slices — over the new config, without dropping the listener. Handlers keep serving through the rebuild; the next request sees the new state. The startup sequence itself is unchanged: hot apply is the startup assembly performed again on a validated config, not a second wiring mechanism.
- **D3 — `GET /api/status` becomes the session-gated mount probe.** The read shrinks to the pair `{ status, authenticated }` behind the [ADR-007](./007-management-cookie-auth.md) session gate: the SPA's mount probe keeps its one round trip, and the boundary's inventory reads are re-homed by the contract rewrite that implements this ADR (`meta[]` moves per D4). The boundary keeps its one response language for the probe: the OpenAI envelope from `src/httpapi/errors.ts`.
- **D4 — `meta[]` lives on `GET /api/models`; the ADR-011 live listing stands and carries the on-demand discovery in its `discover=1` variant ([ADR-016](./016-discover-folded-into-live-listing.md)); the metadata store keeps its startup seeding.** The alias-metadata projection is a dedicated catalog read on this boundary, not a status section. `GET /api/upstreams/:id/models` ([ADR-011](./011-management-live-model-listing.md)) is the one live facility: a pure read without the parameter, and with `discover=1` it fetches fresh entries through the interface's mandatory `listModels()` within one probe budget — retain-last-good store semantics ([ADR-012](./012-alias-model-metadata.md)) — over exactly the named upstream, path-targeted, swapping the slice wholesale before the answer; the store stays seeded once at startup from the ok probes' retained catalogs, exactly as ADR-012 decided, and the CRUD create/update probes seed or clear the affected upstream's slice (D8).
- **D5 — The SPA ships in the same change.** The contract's "API spec leads, UI follows" (Breaking Change Checklist item 5) keeps its ordering within the change and loses its "later change" slack: the endpoints, their contract rows, their `OPENAPI_ROUTES` entries and `bun run apidocs` regeneration ([ADR-013](./013-openapi-docs-surface.md)), and the SPA's management sections that consume them land together. The boundary never presents a mutating API its own operator UI cannot drive.
- **D6 — Deleting an in-use resource answers `409` with code `resource_in_use`; no cascades.** A DELETE whose target is referenced by live configuration (an upstream named by a model route, a client whose alias ACL names a model, a model alias itself) is answered `409 resource_in_use` from the single error mapper, and nothing else is removed with it. Referential integrity is the operator's to resolve, in the order the operator chooses; the gateway refuses the one move that would silently rewrite unrelated configuration.
- **D7 — An absent `apiKey` means keep-existing; the literal `[Configured]` is rejected (as amended by [ADR-018](./018-uniform-optional-value-write-policy.md)).** Create requires a key; update without an `apiKey` field keeps the stored credential — the masked view never carries the value back, so the operator has nothing to echo and the absent field is the only honest "unchanged". A client that sends the mask literal `[Configured]` (the redacted view's own constant, `src/config/redact.ts`) as a key receives a validation problem: the mask is a display fact, never an acceptable credential. The masking rule itself (invariant 9) is untouched — every read keeps serving masks only. As amended by ADR-018: the clear signal (`null` or the exact `""`) on an update is refused — `400`, `cannot be cleared` — a whitespace-only value is refused on both create and update, and the same keep / clear / reject table governs `tlsFingerprint` and `proxy` on the wire and all three fields in the file ([gateway-management.md](../contracts/gateway-management.md), "Optional values in a write body — keep / clear / reject").
- **D8 — Create and update probe synchronously, within the startup probe budget; failure is data, not cancellation.** A create or update runs the startup-style probe against the affected upstream before answering, within the same 10s budget the startup probe and the ADR-011 listing use. A failed probe is reported as data in the response (the outcome the operator asked for) — the mutation still lands, exactly as a config-file edit with a currently-down provider lands at startup. The probe is a report, never a gate: availability is not validity, and validity is D1's job.
- **D9 — A routing-table rebuild resets route health and session affinity.** The in-memory route-health state and the session-affinity bindings ([ADR-010](./010-session-affinity.md)) are keyed to the assembled table; a hot-apply rebuild (D2) drops both and the rebuilt table starts from the neutral state. Affinity re-binds on the next request; the alternative — carrying stale health verdicts or bindings across a table whose routes may no longer exist — is a correctness bug wearing a performance costume.

## Consequences

Positive:

- Operators manage the gateway through the same authenticated surface that reports on it; the hand-edit-plus-restart loop disappears for every routine change, and the SPA (D5) makes it visible.
- D1 keeps one source of truth and one validator: the runtime path and the startup path consume the same grammar, so a change made over HTTP survives a restart by construction, and there is no second representation to reconcile.
- D6 turns referential integrity into a visible error instead of a silent cascade; D7 turns credential immutability into an operator-shaped contract (absent = unchanged) that never echoes a secret.

Negative:

- **The security model carries three mutation-extended invariants:** invariant 1 (provider keys in exactly two places — a created or updated key transits a request body into those same two places, never a third) and invariant 14 (client keys, same reasoning) name the mutation path, and invariant 13 (the sanctioned mutations on `/api/*`) enumerates the three mutation kinds — the auth actions, the CRUD write-back, and the metadata-store swaps (the listing's `discover=1` run and the CRUD probes' seed/clear). This ADR is the documented reason; the rewrites land in the same change.
- **"No files written at runtime" is revoked point-wise:** the contract's Data Flow ("no file reads at request time") and the gateway's keeps-no-state-beyond-the-config-file posture hold for every request except the mutating ones, which write exactly one file — `config.json`, via tmp + atomic rename (D1). The revocation is scoped to the write-back and to nothing else.
- **HTTP behind the session gate becomes a second secrets channel.** Upstream and client credentials now enter through request bodies as well as the config file — always past the [ADR-007](./007-management-cookie-auth.md) session gate, never into a log line, an error envelope, a response body, or the redacted view; D7 keeps them un-echoable. The channel is new; the custody rules are the existing ones, extended to cover the transit.
- The same-change scope (D5) is large by design: endpoints, contract, security model, OpenAPI regeneration, and SPA sections land as one change.
- A mutating boundary is a larger attack surface than an observing one: every CRUD endpoint inherits the session gate, the envelope, and the masking rule, but the class of damage a stolen session can do grows from "read state" to "rewrite config" — the loopback default and the session TTL carry more weight than before.

## Alternatives Considered

- **In-memory only (no write-back):** rejected — the config file would silently stop describing the running gateway: every restart would revert operator changes, and any consumer of `config.json` (a deployment script, a second gateway instance) would read pre-mutation truth. Two states describing one gateway is the failure D1 exists to prevent.
- **A separate runtime store (endpoints write a side file or database):** rejected — a second source of truth next to the config file forks credential custody, duplicates validation, and forces an merge rule ("which of the two wins on restart?") that has no safe answer. The config file already is the authority; the decision extends it rather than paralleling it.
- **Restart-only CRUD (write-back without hot apply):** rejected — it solves persistence but not operability: every change still costs a process restart (dropping in-flight streams, clearing sessions and affinity anyway), so the CRUD surface would be imperceptible to an operator — an API that only works by stopping the thing it manages. D2 is what makes the boundary's new capability real.
