# ADR-008: Cookie-session auth for the management surface (stage 1)

## Status

Accepted

## Context

Gateway-auth is the documented TODO of the request lifecycle: the auth stage runs first in [data-flow.md](../architecture/data-flow.md) and is a no-op placeholder in `src/httpapi/app.ts`, while the listener binds loopback by default precisely because nothing authenticates a client ([security-model.md](../architecture/security-model.md)). Meanwhile the gateway grew an operator-facing surface: the SPA at `/ui/*` consumes `GET /api/status` and `GET /api/configuration` ([gateway-management.md](../contracts/gateway-management.md)) — the sanitized configuration reveals the full upstream inventory (ids, types, baseUrls) and listener layout to anyone who can reach the listener. The loopback default protects the MVP, but a deployment that binds a private interface (the documented, deliberate choice) exposes the management reads to everyone on that network.

Three questions had to be settled before any auth code could exist.

**Scope.** Which surfaces does stage 1 gate? The management surface (`/api/*`) is the one with secrets behind it, and the SPA is the reason it exists. The LLM surface (`/llm/v1/*`) is spoken by OpenAI-protocol SDK clients; cookie auth there would force every SDK integration to carry a cookie jar, and the gateway already drops the client's `Authorization` at the edge ([client-gateway.md](../contracts/client-gateway.md)). The LLM surface deserves its own credential contract — a Bearer token against OpenAI clients — as a separate stage.

**Mechanism.** HTTP Basic (stateless, zero SPA change, the browser's native prompt) versus cookie sessions (a login form in the SPA, real logout, server-side session state). The tipping point is the terminal state, not the first commit: Basic has no logout and replays credentials on every request from a cached browser prompt, while a session cookie is revocable, expires, and gives the SPA a real login/logout UX. The management API stays equally addressable by non-browser clients — they authenticate the same way (one login POST, then the cookie).

**The read-only rule.** `POST /api/login` and `POST /api/logout` are mutations on a prefix whose contract says read-only ([gateway-management.md](../contracts/gateway-management.md), breaking-change checklist item 3: an ADR + security-model + data-flow update before implementation). The rule's purpose is protecting observation state — no endpoint may change what the management reads report. Issuing and revoking an operator session changes no such state; it is the gate for the reads, not a write behind them. The exception needs to be explicit and enumerated, not silent.

## Decision

- **Stage 1 gates the management surface only: `/api/*`.** The SPA shell (`/ui/*`) and the root redirect stay public — the shell is static and data-free; every byte of data arrives from `/api`, and the SPA renders its login card on the first `401`. `/llm/v1/*` stays open and stays the documented auth TODO — stage 2 is a Bearer-token contract for OpenAI clients (this ADR does not decide it).
- **Cookie sessions, config-backed single operator.** `POST /api/login` takes a JSON `{ user, password }` and answers `200` with `Set-Cookie`; `POST /api/logout` revokes the session. Sessions live in memory only: a 32-byte random token, absolute TTL 24h, a bounded store (64 sessions, oldest evicted), cleared on restart — a restart invalidates sessions by design (fail-closed). The cookie is `HttpOnly`, `SameSite=Strict`, `Path=/`, `Max-Age=TTL`, and `Secure` when the listener serves TLS. Failed logins answer after a fixed delay; the user comparison is timing-safe with dummy-hash leveling. There is no lockout, no lockout state, and no second user in stage 1.
- **Credentials live in the config file: a top-level optional `auth` block** — `{ enabled, user, passwordHash }`. The explicit `enabled` switch mirrors the `tls.enabled` precedent ([ADR-007](./007-tls-listener-server-block.md)): the block without `enabled` never validates, and `enabled: false` keeps the material staged while auth stays off. `passwordHash` is an argon2id PHC string generated by `tools/hash-password.ts`; verification uses `Bun.password.verify` (no new dependencies). An absent block or `enabled: false` reproduces today's behavior byte-for-byte.
- **Login/logout are the only `POST` endpoints on `/api/*`** — the enumerated exception to the read-only boundary. Everything else on the prefix stays `GET`-only and observational.
- **The hash enters the HTTP layer only as the entry-point-injected auth slice** — passed from the validated config into the auth gate separately from the redacted view ([security-model.md](../architecture/security-model.md)): the management view carries only the fixed mask for `passwordHash`, and the hash, the plain password, and session tokens never appear in a log line, an error message, or a validation problem line (the logging censor already covers `authorization`/`cookie`/`token` shapes).
- **The 401 is an OpenAI-envelope error** from the single mapper (`src/httpapi/errors.ts`), sent without `WWW-Authenticate` — no native browser prompt; the SPA's own login card is the only login affordance.

## Consequences

Positive:

- The management surface has a real operator identity: config view and probe outcomes stop being world-readable the moment `auth.enabled` flips to `true`.
- Non-browser clients keep first-class access: one `POST /api/login`, then the cookie — curl, scripts, and monitoring authenticate exactly like the SPA.
- Config-only setup: no user database, no persistence layer, no new dependency (`Bun.password` is built-in).
- The auth stage placeholder finally has an implementation to grow into: stage 2 (LLM Bearer) extends the same stage instead of inventing a second one.

Negative:

- `/llm/v1/*` remains unauthenticated in stage 1 — the loopback/private-interface binding default stays the load-bearing protection for the LLM surface and is still the documented advice.
- A gateway restart logs operators out (in-memory sessions); long-running dashboards must re-login after a deploy.
- The session cookie is a bearer credential for its TTL: `HttpOnly` keeps it out of script reach, but a stolen cookie value works until expiry or restart.
- Single user, no roles: anyone who can log in sees everything the management surface shows. Multi-user support is a schema change (`auth` becomes an array) deliberately deferred.
- The fixed failed-login delay blunts online brute force only; it does not defend an exposed listener against distributed attempts — binding guidance (loopback/private) stands.

## Alternatives Considered

- **HTTP Basic for stage 1**: rejected — no logout, credentials replayed on every request from the browser's cached prompt, and the native dialog cannot be restyled or integrated with the SPA; workable as a stopgap, but session flow was chosen as the end state, not a waypoint.
- **Gate `/llm/v1` with sessions in stage 1**: rejected — OpenAI SDK clients would need cookie jars for a protocol surface that has a natural credential type of its own; a Bearer-token stage is the correct contract there and is deliberately left undecided by this ADR.
- **Protect the `/ui` shell with the session**: rejected — the shell is static and carries no data; gating it adds a redirect flow to the static mount while all protected bytes already live behind the `/api` gate. A gated shell with an open API would protect nothing; the reverse is what ships.
- **Stateless signed cookie (JWT / HMAC token)**: rejected — introduces a second secret into the config for revocation the design does not need, and restart-invalidates nothing (sessions would survive a credential change until token expiry); the in-memory Map is simpler and fails closed.
- **Persistent session store (file, SQLite)**: rejected — the MVP has no persistence layer anywhere; adding one for login sessions inverts the effort/benefit at single-process scale, and restart-invalidated sessions are the documented, acceptable behavior.
- **Multi-user `auth.users[]` array now**: rejected — stage 1 needs exactly one operator identity; the array shape is a schema change away ([configuration.md](../domains/configuration.md)) when a second operator actually appears, and a flat single-user block keeps validation and the redacted view small until then.
- **Native browser prompt via `WWW-Authenticate` alongside the session flow**: rejected — two login affordances double every failure path; the SPA login card is the only one.
