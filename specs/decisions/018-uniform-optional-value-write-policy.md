# ADR-018: Uniform optional-value write policy — keep / clear / reject

## Status

Accepted

## Context

Three fields at the management write boundary carry an optional value: `apiKey` (a required credential on every `upstreams[]` and `clients[]` entry), `tlsFingerprint` (an optional SPKI pin — [ADR-004](./004-per-upstream-tls-pinning.md)) and `proxy` (an optional outbound URL — [ADR-017](./017-per-upstream-outbound-proxy.md)). Each is read by two grammars built over the same validator helpers (`src/config/schema.ts`): the FILE grammar — the startup loader's `validateGatewayConfig`, which reads a whole entry from `config.json`, reports every problem to stderr and exits 1 — and the WIRE grammar — the runtime store (`src/config/store.ts`), which reads a request body as a patch over a stored entry and answers a validation problem as the `400` envelope ([gateway-management.md](../contracts/gateway-management.md)). [ADR-014](./014-runtime-management-crud.md) D7 settled one field on one path — an absent `apiKey` on an update keeps the stored credential, and the redacted view's mask literal `[Configured]` is rejected — and everything else grew by accretion.

The two grammars, and the three fields under them, disagreed. A whitespace-only `tlsFingerprint` / `proxy` read as "no value" on both paths — the file as not set, the wire as an explicit clear — so a half-deleted placeholder could silently widen upstream trust from fail-closed pinning to system-CA verification ([ADR-004](./004-per-upstream-tls-pinning.md)) or silently change the egress topology ([ADR-017](./017-per-upstream-outbound-proxy.md)), and the same whitespace in an `apiKey` was accepted by the file as a credential (its check was `length === 0`). On the wire, `null` meant keep for one field and clear for the other two: a `null` `apiKey` on an update kept the stored credential "like an omitted one" while a `null` pin or proxy cleared it, so the one JSON token a client reaches for to say "nothing here" did three different things depending on the key beside it. The contract carried the whole rule in one sentence with three parenthetical exceptions, and the OpenAPI descriptions and the SPA's client-side grammar each restated a slice of it.

The question: what does each of the three fields say, on each path, for each of the shapes a value can take — absent, `null`, the exact empty string `""`, whitespace-only, a real value — and where does that rule stop?

## Decision

- **D1 — One optional-value rule for the three fields, read by both grammars: absent / `null` / `""` are "no value"; whitespace-only is never a value and never a clear; anything else is the field's own grammar.** The rule's normative table lives in [gateway-management.md](../contracts/gateway-management.md) ("Optional values in a write body — keep / clear / reject"); this ADR records the same table:

  | value | `apiKey` (required credential) | `tlsFingerprint` (optional pin) | `proxy` (optional URL) |
  | ----- | ------------------------------- | -------------------------------- | ---------------------- |
  | absent | file: problem, missing · wire create: `400` missing · wire update: **keep** | file: not set · wire create: not set · wire update: **keep** | file: direct · wire create: not set · wire update: **keep** |
  | `null` | file: problem, non-empty · wire create: `400` missing · wire update: **`400` cannot be cleared** | file: not set · wire create: not set · wire update: **clear** | file: direct · wire create: not set · wire update: **clear** |
  | `""` (exact) | file: problem, non-empty · wire create: `400` non-empty · wire update: **`400` cannot be cleared** | file: not set · wire create: not set · wire update: **clear** — the same signal as `null` | file: direct · wire create: not set · wire update: **clear** — the same signal as `null` |
  | whitespace-only | file: **problem** · wire create: `400` whitespace-only · wire update: `400` whitespace-only | file: **problem** · wire create: `400` whitespace-only · wire update: `400` whitespace-only | file: **problem** · wire create: `400` whitespace-only · wire update: `400` whitespace-only |
  | `[Configured]` | file: not checked · wire: `400` mask literal | file: not checked · wire: `400` mask literal | file: not checked · wire: `400` (not a URL) |
  | a real value | file: a non-empty string · wire: a non-empty string, else `400` | file and wire: base64 of the SHA-256 SPKI digest after every whitespace character is stripped, else `400` | file and wire: an `http:` / `socks5:` URL with an explicit port and no userinfo, path, query or fragment, stored trimmed, else `400` |

  The wire's one extra reading is **keep**: a body is a patch over a stored entry and the masked view never carries a credential back, so an absent field is the only honest "unchanged" (ADR-014 D7). The file has no keep — it is the whole entry. The file's one extra verdict is the startup problem for a required `apiKey` with no value; the wire answers the same case as the `400` envelope. Every refusal is a value-free problem line naming the key and the rule ([security-model.md](../architecture/security-model.md)).
- **D2 — A whitespace-only value is a problem on both paths, for all three fields.** Whitespace is the signature of a client or authoring bug — a half-deleted placeholder, a form that submits its padding — never an intentional clear; the one honest spelling of "no value" is absent, `null` or `""`. Reading it as "no value" made a pin vanish silently (fail-closed → system-CA, ADR-004) or changed the egress topology silently (ADR-017); reading it as a credential stored `"   "` as an upstream key. The rule is about a value that is nothing but whitespace: a non-empty pin's internal whitespace is still stripped (a pin pasted with line wraps still matches), and the proxy is still stored trimmed.
- **D3 — `null` and `""` are one clear signal, and a required credential cannot be cleared.** No credential-less upstream or client exists, so the clear signal on an `apiKey` is refused on an update (`400`, `cannot be cleared` — send a new value, or omit the field to keep the stored one) and reads as missing / empty on a create. On the two optional fields the same signal clears: a `null` or `""` pin leaves the entry without a pin, a `null` or `""` proxy leaves it with a direct connection — the stored entry never carries `tlsFingerprint: ""` or `proxy: ""`.
- **D4 — The mask literal `[Configured]` is rejected on the wire only (ADR-014 D7).** The redacted view is the only thing that produces the mask, so only a client echoing a view back can submit it; a hand-edited file has no view to echo, and the file grammar does not check for it — `"apiKey": "[Configured]"` in `config.json` is a non-empty string like any other (an odd credential, not a mask violation).
- **D5 — Scope: the rule covers exactly the three optional-value fields on upstream and client writes.** Identity keys (`type`, `id`, `baseUrl`, `name`, `alias`) are not optional values: on the wire a `null` on one is inherited — the null rule, it reads as omitted and the stored value is kept on an update, missing on a create — and in the file they are required. The wholesale blocks on a model write — `limits` (the block and each single limit) and `weight` — are PUT-replace semantics (a `null` or absent block leaves the entry without it), not keep / clear / reject. Every other key follows the null rule.

## Consequences

Positive:

- One rule, one table, two consumers: the same bytes get the same verdict from `config.json` and from a request body, so an operator can move a value between the two without a semantic change, and a client (the SPA included) needs one grammar, not one per field per path.
- A whitespace-only value fails loudly on both paths — a half-deleted placeholder never silently drops a pin, never silently reroutes egress, and never serves as a credential.
- `null` and `""` are interchangeable spellings of clear on the optional fields; a client need not remember which one a field prefers. A required credential answers the clear signal with a refusal that names the remedy, so a client bug is visible instead of silently keeping a key the operator meant to rotate.
- The contract, the OpenAPI descriptions (`WRITE_GRAMMAR_POLICY`, `src/httpapi/openapi.ts`) and the store's header carry the same table; the test suites (`src/config/schema.test.ts`, `src/config/load.test.ts`, `src/httpapi/handlers/*.test.ts`) pin its rows on both paths.

Negative:

- **`""` on the wire is an explicit clear.** A client that renders an empty form field and submits it as `""` clears a stored pin or proxy it meant to keep. Every client MUST trim its fields and omit the empty ones — the SPA does (`web/src/sections/Upstreams.tsx`, `web/src/sections/Clients.tsx`: a field rides the body only when its trimmed value is non-empty; the rule is [frontend.md](../domains/frontend.md)'s). The cost is accepted because the file grammar already read `""` as "no value", and refusing it on the wire would split the two grammars on the most common rendering of an empty optional field.
- **Startup-breaking.** A `config.json` carrying a whitespace-only `apiKey`, `tlsFingerprint` or `proxy` no longer validates — the gateway refuses to start with a value-free problem line (`upstreams[i]: tlsFingerprint must not be whitespace-only — omit the key, use null or "" for no value`, the same for `proxy`; `apiKey must be a non-empty string`). A file that previously started — reading the whitespace as "no pin", "direct" or a credential — is now a startup failure; the fix is to delete the key or write `null` / `""` (for `apiKey`, a real value).
- **Wire-breaking for API clients.** `PUT` with `apiKey: null` answers `400 cannot be cleared` (it kept the stored credential); `PUT` with `apiKey: ""` answers `400 cannot be cleared`; a whitespace-only `tlsFingerprint` / `proxy` answers `400` on create and update (it cleared on update). Clients that relied on those readings must send `null` / `""` for the optional fields and a real value — or nothing — for the credential.
- The two paths word their refusals differently (the file names the entry by its index, the wire by its kind; only the wire's clear line can offer "keep" as the remedy). The verdict is uniform; the prose is not.

## Alternatives Considered

- **(a) `apiKey: null` = keep — an exception for the required secret:** rejected — it makes `null` mean two things on one boundary (keep for `apiKey`, clear for `tlsFingerprint` / `proxy`), so a client that renders an untouched field as `null` keeps a credential while the same token beside it clears a pin, and a client that means to clear cannot tell its intent from its bug. The uniform reading serves the credential better too: the clear signal meets a refusal that names the remedy, not a silent keep that hides the mistake.
- **(b) Strict wire — `""` → `400`:** rejected — `""` is the natural rendering of an empty optional field (a cleared input, a form serializer, a JSON literal), and the file grammar already reads it as "no value" for the two optional fields; refusing it on the wire would split the grammars on their most common input and force every client to rewrite `""` into `null` or an omission for no safety gain — `""` carries no information `null` does not. For `apiKey` the `""` is refused on both paths anyway (cannot be cleared on update, non-empty on create). The cost — an empty field submitted as `""` clears — is bounded by the client rule (trim, omit the empty) the SPA already follows.
- **(c) Whitespace-only = clear — the previous wire reading:** rejected — whitespace is a bug signal, not an intent: a half-deleted placeholder, a field padded by its editor, a value pasted with a trailing newline. Reading it as a clear made a pin vanish silently (fail-closed pinning → system-CA verification, [ADR-004](./004-per-upstream-tls-pinning.md)) or flipped the egress topology silently ([ADR-017](./017-per-upstream-outbound-proxy.md)) on the strength of bytes nobody chose to send; reading it as "no value" on the file path did the same at startup, and as a credential it stored padding for a key. The one honest clear is `null` or `""`; whitespace-only is refused on both paths, and the SPA's trim-before-send rule keeps a padded field from ever reaching the wire as a problem.
- **(d) Document the current behavior as is:** rejected — "as is" was two grammars disagreeing: the wire cleared on whitespace-only where the file read it as not set, `null` kept a credential while it cleared a pin, and the file accepted whitespace as a credential. The contract's one sentence carried three parenthetical exceptions, and the OpenAPI and SPA prose each carried a different slice. Writing that down more clearly would preserve the bug, not decide it; the decision is cross-cutting (config schema, store, HTTP handlers, OpenAPI, SPA), startup-breaking, and had real alternatives — the ADR bar is met.
