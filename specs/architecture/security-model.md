# Architecture: Security Model

## Context

The gateway is a credential custodian: it holds provider API keys that clients must never see, and it forwards untrusted client traffic to trusted upstreams. Stage 1 of gateway-auth gates the management surface (`/api/*`) with a config-backed cookie session ([ADR-008](../decisions/008-management-cookie-auth.md)); the LLM surface (`/llm/v1/*`) remains unauthenticated — the remaining gateway-auth TODO (see the request lifecycle in [data-flow.md](./data-flow.md)) — so the active protections are the session gate, key storage rules, log redaction, and the trust boundaries below. They must hold in both modes: auth enabled and the legacy auth-off config.

## Trust Boundaries

```
     UNTRUSTED                                TRUSTED
+------------------+                +------------------+
|     clients      |                |    providers     |
| arbitrary        |                |      APIs        |
| request bodies   |                |   authenticated  |
| unknown identity |                |  by provider key |
+------------------+                +------------------+
        |                                    ^
        | HTTP or HTTPS                      | HTTPS + provider key
        | server TLS only, no client auth    | credentials from config only
        v                                    |
+------------------------------------------------------------------+
|                             gateway                              |
|  request stages: auth (session gate on /api/* when auth   |
|  enabled -- ADR-008; /llm/v1 ungated until stage 2) ->    |
|  route -> prefix -> upstream -> proxy stream;             |
|  key storage + log redaction rules                        |
+------------------------------------------------------------------+
```

- Inbound: every client request is untrusted regardless of route. Stage 1 gates `/api/*` with the config-backed session when `auth.enabled` is true; the LLM surface `/llm/v1/*` and the static shell stay ungated, so the listener binds to loopback or a private interface only — that binding is the load-bearing protection for the ungated surfaces. A TLS-enabled listener ([ADR-007](../decisions/007-tls-listener-server-block.md)) changes the transport only — HTTPS encrypts the link and authenticates nobody, so the ungated LLM surface and the loopback default stand unchanged.
- Outbound: the gateway authenticates to provider APIs only with credentials from its config; client-supplied credentials never travel upstream. A configured `tlsFingerprint` narrows that trust further: the pinned upstream is identified by its SPKI key alone — fail-closed probe, leaf-anchored chain, per-connection pin veto ([ADR-005](../decisions/005-per-upstream-tls-pinning.md)) — and its chain need not be publicly trusted. Without a pin, the system CA pool plus hostname verification decide; there is deliberately no third mode that accepts an arbitrary certificate.
- The upstream is trusted to answer OpenAI-dialect requests — and trusted with no more client data than the request itself carries.

## Provider Keys

- Provider API keys exist in exactly two places: the config file and the in-memory field of their upstream instance.
- Keys enter the process only via the config file (kept out of version control); the config path comes from the `LLM_GATEWAY_CONFIG` environment variable (default `./config.json`), key material never does.
- Key flow: config → upstream field → provider credential header on upstream calls. No other component reads the field.
- `GET /llm/v1/models` and error responses expose model ids and statuses only — never keys, never upstream credentials. The management API serves the same rule from the other side: `GET /api/configuration` returns `apiKey` / `tlsFingerprint` as a fixed mask, never the configured values — while the `server.tls` PEM paths are shown verbatim, since a path is not secret — the mask is applied by `redactedConfigView` (`src/config/redact.ts`) in the config domain, at the entry point, before the view enters the HTTP layer ([gateway-management.md](../contracts/gateway-management.md)).

## Operator Credentials

- Stage 1 management auth is a single config-backed operator identity: a top-level optional `auth` block — `{ enabled, user, passwordHash }` — with an argon2id PHC hash generated by `tools/hash-password.ts`. An absent block or `enabled: false` means the gateway behaves exactly as before ([ADR-008](../decisions/008-management-cookie-auth.md)).
- The hash lives in exactly two places — the config file and the in-memory auth slice the entry point injects into the HTTP layer — the same two-place rule as provider keys. It never enters the redacted view (the management view carries only the fixed mask), a log line, an error message, or a config-validation problem line ([configuration.md](../domains/configuration.md)).
- The plain password exists only inside `POST /api/login` request handling: verification is `Bun.password.verify` against the configured hash, the user comparison is timing-safe with dummy-hash leveling, and failed logins answer after a fixed delay.
- Sessions are in-memory only: a 32-byte random token, an absolute TTL, a bounded store, cleared on restart; the cookie is `HttpOnly`, `SameSite=Strict`, `Path=/`, and `Secure` under TLS. Session tokens never appear in a log line (the logging censor already covers `cookie`/`authorization`/`token` shapes).

## Redaction in Logs

- Logging is leveled (trace/debug/info/warning/error/none) and writes to stderr. The logging layer redacts a fixed set of sensitive fields (authorization, x-api-key, api-key, cookie, token) before emitting any line, at every level including trace.
- Startup logs upstream ids and types; the raw config is never dumped, and key material never reaches a log line. TLS startup errors may name the certificate/key file paths — paths are not secret; the PEM file contents never do, and the listening line carries only the fact of TLS (enabled or not), never file material.
- Upstreams log outcome metadata only — the startup probe result, and code/reason fields on synthesized failures; request and response bodies are never logged at any level, so provider payloads never reach a log line ([observability.md](../domains/observability.md)). The per-request summary line (method, path, status, duration) belongs to the HTTP middleware, not to upstreams.
- Upstream failure logs carry only the upstream status, a code, and a gateway-authored reason — provider error payloads (which sometimes echo request headers) are relayed to the client verbatim but never echoed into a log line.

## Invariants

1. Provider API keys are stored in exactly two places: the config file and the in-memory field of their upstream instance.
2. No provider key, client credential, or sensitive header value ever appears in a log line, an HTTP response body, or an error message the gateway emits.
3. The logging layer redacts sensitive field values before emission, at every level including trace.
4. Upstreams attach their own credentials at the upstream boundary; client-supplied authorization headers are never forwarded upstream.
5. The auth stage precedes routing and upstream invocation in the request lifecycle, and no code path reaches an upstream without passing through it. When `auth.enabled` is true, the stage gates `/api/*` with the config-backed session — `POST /api/login` and `POST /api/logout` are the only requests it serves without one; the `/llm/v1/*` surface and the static shell stay ungated until the stage-2 Bearer contract ([ADR-008](../decisions/008-management-cookie-auth.md)).
6. While the LLM surface is unauthenticated (stage 1 gates only the management surface), the listener binds only to loopback or a private interface.
7. Startup logging names upstreams (id, type) but never prints key material or the raw config.
8. A configured `tlsFingerprint` always fails closed on a pin mismatch — a pinned upstream that presents any other key surfaces as `502 upstream_tls_error`, never as a relayed response or a warning-and-continue ([ADR-005](../decisions/005-per-upstream-tls-pinning.md)).
9. The management configuration view (`GET /api/configuration`) carries masked values only: `redactedConfigView` (`src/config/redact.ts`) replaces every `apiKey` with the fixed mask `[Configured]` and a configured `tlsFingerprint` with the same mask — `null` when absent — at the entry point, before the view enters the HTTP layer; the raw config never does ([gateway-management.md](../contracts/gateway-management.md), [configuration.md](../domains/configuration.md)).
10. TLS certificate and key files enter the process only through their configured paths, read once at startup before the port binds; their contents appear in no log line, error message, or HTTP response, and the config file carries paths, never PEM material ([ADR-007](../decisions/007-tls-listener-server-block.md), [configuration.md](../domains/configuration.md)).
11. Server TLS is transport, not authentication: `server.tls.enabled` encrypts the client link and nothing else — the auth stage stays in the lifecycle exactly as before, the loopback default stands, and no certificate check substitutes for client auth ([ADR-007](../decisions/007-tls-listener-server-block.md)).
12. The `auth.passwordHash` enters the HTTP layer only as the entry-point-injected auth slice — never through the redacted view (which carries the fixed mask), a log line, an error message, or a config-validation problem line; the plain password exists only inside `POST /api/login` request handling ([ADR-008](../decisions/008-management-cookie-auth.md)).
13. Sessions are in-memory only — a restart clears every session — and `POST /api/login` / `POST /api/logout` are the only mutating endpoints on `/api/*`; session tokens never appear in a log line ([ADR-008](../decisions/008-management-cookie-auth.md), [gateway-management.md](../contracts/gateway-management.md)).

## Anti-Patterns

- Hardcoding a provider key or base URL in upstream source "just for a local test" — keys enter the process only through the config file; a committed test key is a leaked key.
- Forwarding client headers wholesale to the upstream — header pass-through excludes authorization and hop-by-hop headers; the upstream injects its own credentials.
- Logging full upstream request/response bodies at any level "to debug faster" — the MVP logs metadata only; provider payloads never reach a log line.
- Putting key material into an error surface ("upstream rejected key sk-...") — errors carry statuses and provider messages, never credentials.
- Implementing gateway-auth inside individual upstreams (each upstream checking client keys) — auth is one pre-routing stage; per-upstream auth duplicates checks and spreads credential logic into provider code.
- Adding a skip-verification fetch path (`rejectUnauthorized: false`) to "make self-signed upstreams work" — the only non-default acceptance path is the pinned one ([ADR-005](../decisions/005-per-upstream-tls-pinning.md)); a flag that accepts any certificate is a standing MITM window.
- Reading server TLS as client authentication — "it is HTTPS now, auth can wait" conflates transport encryption with identity: `server.tls.enabled` gates the link only, the auth stage remains the sole client-auth mechanism (a no-op today), and the loopback default exists precisely because neither exists yet ([ADR-007](../decisions/007-tls-listener-server-block.md)).
- Exposing the MVP listener publicly "temporarily" before gateway-auth lands, or shipping provider keys to the future admin SPA — the admin surface receives aggregates and statuses, never key material (invariant 9: the mask is applied in the config domain, so no handler below the entry point ever holds a real value to leak).
- Gating the `/ui` static shell while `/api/*` answers without a session — the data boundary is `/api`; a gated shell over an open API protects nothing ([ADR-008](../decisions/008-management-cookie-auth.md)).
- Echoing the configured `passwordHash`, a plain password, or a session token into a log line, an error envelope, or a validation problem line — operator credentials follow the same never-echoed rule as `apiKey` (invariant 12).
